Wiki transversal · /wiki

Memoria viva del proyecto, transversal a todas las áreas (Producto, Marketing, RRHH, Operaciones). Procesa sources brutos (artículos, reuniones, notas, transcripciones) y los sintetiza en páginas semánticas con wikilinks [[slug]]. La gestiona age-spe-wiki-curator.

Estructura física

raw/ es la fuente de verdad inmutable. docs/general/wiki/ es síntesis derivada (regenerable).

raw/
├── articulos/         // blogs, papers, recursos externos
├── reuniones/         // asistentes, agenda, decisiones, action items
├── notas/             // capturas rápidas, ideas
├── transcripciones/   // audio→texto
└── otros/

docs/general/wiki/
├── README.md   index.md   log.md   tags.md
├── entities/          // personas, herramientas, APIs, productos
├── concepts/          // decisiones, patrones, principios
├── topics/            // áreas / temas exploratorios
└── sources/           // summaries de cada raw + citations

Disciplina (reglas de captura en CLAUDE.md)

  1. Source nuevo: si pegas un artículo o copy-paste largo → "¿lo guardo en raw/ y lo ingesto?"
  2. Entidad/concepto nuevo: si aparece persona/librería/API → "¿creo entity page?"
  3. Reuniones: si mencionas "tuve una reunión con X" → ejecuta /wiki reunion.
  4. Antes de responder consultas no-triviales: lee la wiki primero. Cita con wikilinks.
  5. Filtrar buenas respuestas: si tu respuesta es densa y valiosa → "¿la archivo como concept page?"
  6. Action items de reuniones → tareas PM: sugiere /pm capture, no ejecutes automáticamente.

Curator nunca: modifica raw existente · escribe a docs/<area>/ · invoca a otros agentes · crea entity/concept sin confirmación.

Sub-indicador en cada card (⏸ pendiente / ✅ completado)

Cada card muestra si el agente ya hizo su parte:

  • ⏸ pendiente: tarea está en la columna pero el agente NO ha sido lanzado. El artefacto esperado no existe en filesystem.
  • ✅ completado: el agente terminó. El artefacto esperado (research.md, stories.md, etc.) existe.

Cuando una tarea está ⏸ pendiente, la card muestra un botón 📋 /comando que copia el comando al portapapeles para que lo pegues en Claude Code.

Cuando está ✅ completado, la card muestra una sugerencia textual: "⤷ Próximo: arrastra a Planning y lanza /plan".

Columna "Definición" — 3 rutas alternativas

La columna definicion puede ser ejecutada por 3 agentes distintos según el contexto. Pablo elige qué comando lanzar:

  • Hay diseños en Pencil → /design-discovery (opcional, captura lógica funcional vía entrevista al PM) → /design-to-prd (design-analyst)
  • Existe research.md previo → /define (jtbd-architect + story-writer enriquece)
  • Idea autónoma sin diseños ni research → /story (story-builder)

Los 3 producen stories.md (sub-indicador pasa a ✅ completado), y la tarea avanza igual al siguiente estado.

Transiciones: TODAS LIBRES

Cualquier estado puede ir a cualquier otro. El sistema confía en el humano. Si quieres mover una tarea de hecho a research (bug post-aprobación) o saltar de sin_priorizar directo a build (experimento), se permite.

Si en el futuro quieres restringir transiciones, edita la matriz transitions en pm/config.json → areas.producto.transitions manualmente.

UI del kanban

8 columnas principales (sin_priorizar → hecho) horizontales + tray lateral colapsable a la derecha con bloqueada y cancelada. Click en el botón "▶ Tray" para colapsar/expandir.

Inferencia bootstrap (solo tareas nuevas)

Si una tarea recién creada no tiene status aún, el PM infiere uno razonable según artefactos existentes (qa.md → hecho, build-state.md → build, architecture.md → planning, stories.md → definicion, research.md → research, sprint.md → priorizada, default → sin_priorizar). Una sola vez por tarea: después, el humano controla.

Migración desde V1 (estados viejos)

Proyectos creados antes de V2.0 tenían los 8 estados viejos (en_definicion, en_build, etc.). Para migrar:

bash "$HOME/Desktop/PABLO/Proyectos/AgentArchitect/exports/pmx-product/scripts/migrate-states-v2.sh" "/ruta/proyecto" --apply

El script:

  • Re-mapea status de cada tarea en pm/tasks.json y en frontmatter de stories.md
  • Mueve states/transitions del nivel global de config.json a areas.producto.*
  • Añade state_meta con info de agente/comando/artefacto por estado

PRD evolutivo — secciones se enriquecen con cada comando V3.3

El PRD se crea esqueleto (vacío con placeholders) y se va llenando progresivamente. Cada sección está delimitada por marcadores <!-- AUTO:section --> ... <!-- /AUTO:section -->. El PM en modo dossier (auto-sync post-comando) actualiza solo las secciones AUTO, preservando el resto.

Reglas operativas del enriquecimiento
  • Conservador: si el PRD NO tiene marcadores AUTO (legacy sin migrar), el PM no lo toca. Migrar con script (ver abajo).
  • Defensivo: si el artefacto fuente no existe (ej. aún no hay research.md), la sección AUTO mantiene su contenido [Pendiente].
  • Idempotente: si el contenido extraído coincide con lo escrito, no se escribe (evita actualizar mtime sin motivo).
  • USER:notes preservada SIEMPRE. Sección fuera de marcadores AUTO, los agentes nunca la tocan.
  • Contenido no-AUTO preservado. Secciones extra (Restricciones, Riesgos, etc.) que escribas a mano permanecen intactas.
Migración de PRDs legacy

Para proyectos con PRDs antiguos sin marcadores AUTO (ej. PRDs creados antes de V3.3 por /design-to-prd legacy):

bash "$HOME/Desktop/PABLO/Proyectos/AgentArchitect/exports/pmx-product/scripts/migrate-prd-to-auto-markers.sh" "/ruta/proyecto" --apply

El script:

  • Detecta las 6-7 secciones canónicas por heading (Problema, Métricas, AS-IS/TO-BE, Actores, Scope, Diseño técnico, User Stories)
  • Envuelve cada una en marcadores AUTO
  • Preserva secciones extra (Restricciones, Riesgos, Siguiente Paso...) fuera de marcadores
  • Añade sección USER:notes al final si no existe
  • Backup automático en prd.md.bak-YYYYMMDD-HHMMSS
  • Idempotente: si el PRD ya tiene marcadores AUTO, no se toca

Auto-sync post-comando (V3.1) NUEVO

8 comandos invocan age-spe-pm-producto con modo sync automáticamente al terminar:

/story · /define · /design-to-prd · /plan · /build · /review · /hotfix · /analyze

Esto significa que tras lanzar uno de estos comandos, el dashboard refleja el nuevo estado sin que tú tengas que ejecutar /pm sync manual. Si el sync detecta drift (contradicción entre archivos), se reporta al final del output del comando. Si no, el sync es silencioso.

Comandos sin auto-sync (no modifican estado de tareas): /save · /code-review · /new-project · /unknown-unknowns · /docs · /challenge · /learned · /wiki · /pm (sería recursivo).

Feature Dossiers · /pm dossier NUEVO V3.1

El problema que resolvía esta capa: cuando una idea entraba al sistema, todos los artefactos generados (challenge brief, research, JTBDs, stories, architecture, qa, lessons) quedaban dispersos en carpetas. Para entender una feature había que abrir 6-8 archivos en orden manual. Y las decisiones humanas conversacionales se perdían.

El Feature Dossier es un archivo agregador por feature folder que reúne todo en una vista unificada navegable desde el dashboard.

Estructura

docs/producto/features/<feature>/
├── _dossier.md          // NUEVO — vista agregada auto-mantenida
├── _events.jsonl        // NUEVO — timeline cronológico append-only
├── research.md          // existente (de /analyze)
├── jtbds.md             // existente (de /define)
├── stories.md           // existente (de /define)
├── architecture.md      // existente (de /plan)
└── challenge-brief.md   // existente (de /challenge)

Lifecycle

  1. Cualquier comando del pipeline ejecuta /pm sync + /pm dossier all al terminar (auto-sync).
  2. El PM detecta qué feature folders se han modificado en los últimos 60s.
  3. Para cada una, lee TODOS sus artefactos + tasks.json + sprint.md + qa.md.
  4. Regenera _dossier.md rellenando 10 secciones (Estado · Idea · Challenge · Análisis · Definición · Arquitectura · Sprint · Build · Review · Aprendizajes · Decisiones · Artefactos).
  5. Append un evento a _events.jsonl describiendo lo que el comando hizo.

Idempotencia + sección de usuario

Marcadores <!-- AUTO:section --> delimitan zonas auto-generadas. La sección <!-- USER:notes --> está fuera de los marcadores AUTO: el PM nunca la sobrescribe. Pablo puede editar sus notas libremente en cualquier momento.

Ejecutar /pm dossier all dos veces produce el mismo dossier (excepto last_updated_at). Los eventos en _events.jsonl NO se duplican (detección por (ts, agent, event, entity)).

Decisiones humanas críticas en el timeline

4 comandos (/analyze, /define, /plan, /hotfix) capturan decisiones críticas como evento agent: "human":

  • Proceder con Quality Guard score <7 sin corregir gaps
  • Override del quality-coach (mantener story tal cual)
  • Aprobar ADR de arquitectura con tradeoffs
  • Confirmar resolución de bug (en hotfix)

Las aprobaciones rutinarias NO se logan — solo las críticas.

Vista en el dashboard

Nueva sub-pestaña Dossiers entre Funcionalidades y Kanban. A la izquierda lista de features con buscador, a la derecha el dossier renderizado completo + timeline visual de los eventos. Las decisiones humanas se destacan en color naranja.

Migración para proyectos existentes

Script scripts/regenerate-dossiers.sh /ruta/proyecto --apply crea esqueletos de dossier para todas las features ya existentes. Tras esto, ejecuta /pm dossier all en Claude Code para rellenarlos con la información real.

El dossier es derivado, no fuente. Si lo borras, se regenera desde los artefactos atómicos. Los .md de research, stories, architecture, etc. siguen siendo la única fuente de verdad.

Captura proactiva con /learned

Cuando resuelvas algo difícil, lánzalo. Te pregunta qué pasó, por qué, cómo lo resolviste, qué hacer diferente. Clasifica en 7 categorías (bug, edge-case, performance, architecture, tooling, process, mistake) y escribe en lessons.md + MEMORY.md.

Cuando MEMORY.md supera 200 líneas, las entradas antiguas se archivan en memory/archive/[YYYY-MM].yaml (retención: 1 año).

Project Registry · inventario técnico

Problema que resuelve: sin registry, cuando creas Feature B los agentes no saben qué tablas/APIs/componentes ya creó Feature A. Con registry, todo está conectado.

Archivo único

docs/general/project-registry.md — 6 categorías base obligatorias en formato tabla:

  • DB Models: tablas, campos clave, relaciones, feature origen, status.
  • API Endpoints: método, path, auth, feature origen, status.
  • Shared Components: nombre, path, props/interface, feature origen.
  • Services & Utilities: nombre, path, exports clave, feature origen.
  • Types & Interfaces: nombre, path, campos clave, feature origen.
  • External Integrations: servicio, propósito, feature origen, status.

Ciclo de vida de assets

  1. planned: una story se crea (/design-to-prd, /define, /story) y los assets de su sección "Crea" se añaden al registry.
  2. active: /review verifica que el asset existe en el codebase y lo promueve.
  3. deprecated: asset reemplazado o eliminado. Tras 2 sprints se archiva.

Story template: Dependencias del proyecto

Cada story ticket lleva una sección Usa (assets existentes del registry que reusa) + Crea (assets nuevos para añadir al registry). Esto previene duplicación.

No hay /registry. Es automático: /design-to-prd, /define, /story escriben (planned). /plan y /build leen. /review promueve a active. Si el archivo no existe, los comandos saltan la parte del registry sin romperse.

QA Layer · /review

Ciclo de 3 supervisores que corre automáticamente tras cada /review. Verifica calidad, puntúa, propone mejoras. Ningún otro sistema lo tiene.

El ciclo

/review dispara:

  1. test-engineer    Validation loop: tests + coverage + 3 ciclos máx
  2. code-reviewer    Calidad, seguridad, performance (con memoria)
                       │
                       ▼
  ──── QA CYCLE (supervisores read-only) ────
  3. auditor          Compliance con rules/ (binario sí/no)
  4. evaluator        Puntúa 4 dimensiones (0–10)
  5. optimizer        Detecta patrones cross-review, propone mejoras
                       │
                       ▼
  6. PM: "¿Genero docs?"   // SIEMPRE pregunta
       sí → ski-project-docs genera docs/general/exportable/features/[feature].md

5 principios de diseño

1. Analysis Informs, Never Blocks

Los agentes identifican riesgos. El humano decide. Ningún agente puede bloquear progreso. Si /analyze da score bajo, el PM decide si proceder con riesgo o corregir.

2. Supervisors Observe, Never Impose

Los 5 supervisores (auditor, evaluator, optimizer, quality-coach, strategic-challenger) son read-only. Reportan, puntúan, proponen. Nunca modifican código ni stories.

3. Vertical Value Delivery

Cada story debe entregar valor end-to-end (UI → API → DB). Story-splitter rompe horizontales (DB schema → API → Frontend) en verticales (User puede ver lista → puede filtrar → puede ordenar).

4. Evidence Over Assumptions

Quality Guard requiere baseline cuantificada antes de aprobar PRDs. "Reduce clicks 50%" es hipótesis sin baseline. "40% abandono en paso de pago, 7 pantallas, 45 campos" es problema documentado.

5. Minimum Viable Complexity

Usa lo mínimo necesario. Typo → prompt directo. Idea fresca → /story. Feature pequeña → /define + /build. Solo proyecto grande necesita el pipeline completo.

Context engineering

Los agentes no se cargan todos a la vez. Cada uno se ejecuta en su propio contexto separado. Si /define usa 4 agentes, son 4 contextos independientes — la calidad es PEAK para cada uno.

/build va más allá: spawna un sub-agente fresco (200k tokens) por cada story. La story 5 se implementa con la misma calidad que la story 1, sin importar cuántas haya.

Coding Discipline NUEVA

4 principios que atacan los antipatrones más comunes de coding asistido por LLMs (asunciones silenciosas, sobre-construcción, cambios orthogonales, criterios débiles). Los carga rul-llm-coding-discipline en tech-architect, code-reviewer y test-engineer. También aplican a Claude Code directamente cuando edita código.

1. Think Before Coding

No asumas en silencio. Si hay ambigüedad: pregunta. Si hay 2+ enfoques: presenta tradeoffs. Si te confundes: para. Push back honesto cuando algo parece sub-óptimo.

2. Simplicity First

Mínimo código que resuelva. No abstracciones para código de un solo uso. No "flexibility" no pedida. Test del senior: "¿diría sobre-construido?". Si 200 líneas pueden ser 50, reescribe.

3. Surgical Changes

Cada línea modificada debe trazar al request original. No "mejores" código adyacente. Si ves dead code o deuda técnica: menciónalo en el reporte, no lo arregles aquí. Boy Scout Rule: la cleanup va en commit aparte.

4. Goal-Driven Execution

Antes de codear: define cómo se ve "hecho". Transforma imperativo vago → criterio testable. "Arregla bug" → "test que reproduce el bug, hazlo pasar". Multi-step: enuncia plan numerado con verificación por paso.

Origen: notas de Andrej Karpathy sobre LLM coding (dic 2025) + sistematización "Four Principles" de la comunidad. Adaptado al sistema PM x10 con caveat del Boy Scout Rule.

Wiki Discipline

6 reglas en CLAUDE.md de cada proyecto que mantienen la wiki viva. Sin esto, la wiki queda vacía porque nadie alimenta el raw.

  1. Source nuevo: pegas un artículo o copy-paste largo → "¿lo guardo en raw/ y lo ingesto?"
  2. Entidad/concepto nuevo: aparece persona/librería/API → "¿creo entity page?"
  3. Reuniones: mencionas "tuve una reunión con X" → ejecuta /wiki reunion.
  4. Antes de responder consultas no-triviales: lee la wiki primero. Cita con wikilinks [[entities/x]].
  5. Filtrar buenas respuestas: respuesta densa y valiosa → "¿la archivo como concept page?"
  6. Action items de reuniones → tareas PM: sugiere /pm capture, no ejecutes automáticamente.
